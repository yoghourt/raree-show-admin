## 3. ADR Compliance

### 3.1 ADR-004 Decision 2 — Copilot Workflow / Human Acceptance Gate

**Requirement:** AI suggestions SHALL NOT be persisted without explicit human acceptance.

**Evidence:**
- `POST /api/admin/ai/suggest` returns candidates only (AC-01, §14.3).
- `useCopilotSession.accept()` calls `form.setValue()` on form state exclusively — no database write.
- Database write occurs only via existing CRUD form submission path.
- `SuggestionPanel` renders Accept/Skip/AddToQueue buttons — no auto-persist path.

**Verdict: ✅ PASS**

### 3.2 ADR-004 Decision 3 — Narrative Regenerate

**Requirement:** AI regeneration of Narrative fields is permitted at human request.

**Evidence:**
- `NarrativeRegenButton` / `SceneNarrativeRegen` / `LocationNarrativeRegen` components render only on `narrative`-classified fields (classification read from `getClassification()` in the registry — not hardcoded by field name).
- `acceptRegen()` in `useCopilotSession` writes to form state only, NOT the database.
- Regenerate dispatches to `/api/admin/ai/suggest/retry` — same endpoint as Batch Retry.

**Verdict: ✅ PASS**

### 3.3 ADR-004 Decision 7 — No Bootstrap Components

**Requirement:** `BootstrapPanel`, `clearExisting`, batch persist route are explicitly rejected.

**Evidence:**
- grep `BootstrapPanel|clearExisting|bootstrap-provider|/api/admin/ai/bootstrap` across repository → **0 matches**.
- Copilot business logic imports only from `lib/ai/copilot-types`, `lib/ai/field-registry`, `lib/ai/suggest-service`, `lib/ai/copilot-text-llm`, `lib/ai/parse-copilot-value`, `lib/ai/llm-response-utils`, `lib/supabase`, `lib/supabase-server`.
- ADR-001 bootstrap runtime (route, providers, `BootstrapPanel`) was removed; ADR-001 document retained as superseded archive only.
- Shared LLM JSON helpers live in `lib/ai/llm-response-utils.ts` — no bootstrap workflow coupling.

**Verdict: ✅ PASS**

### 3.4 ADR-004 Decision 8 — No Catalog-level Accept All

**Requirement:** Catalog-level or work-level Accept All is prohibited.

**Evidence:**
- `SuggestionPanel.acceptAll` is labeled "全部接受" (Accept All), scoped to currently-visible suggestions in the current entity session.
- `useCopilotSession.acceptAll()` filters `suggestions` state (per-session, per-entity) — no cross-entity mechanism exists.
- grep `catalogAccept|workAccept|accept.*all.*catalog` → **0 matches**.

**Verdict: ✅ PASS**

### 3.5 ADR-004 Decision 9 — Scope Field AI-Generation Prohibition

**Requirement:** AI MUST NOT propose or generate the Scope Field value.

**Evidence:**
- `buildFieldPrompt()`, `buildBatchFieldPrompt()`, and `buildBatchRetryPrompt()` in `suggest-service.ts` explicitly include: `"不要生成或推测实体名称本身"` (Do not generate or infer the entity name itself) — AC-16/SD-02 compliant.
- Batch prompts additionally constrain suggestions to the work's universe (anti cross-universe contamination).
- `getSuggestableFields()` in `field-registry.ts` excludes all `scope`-classified fields from the request.
- Server validates that no scope field appears in `emptyFields` (422 INVALID_FIELD_REQUEST).

**Verdict: ✅ PASS**

### 4.5 Implementation Amendments (Post-Audit, 2026-06-11)

The following changes were made after initial implementation during manual testing. They do **not** violate ADR-004 or SPEC-D2-002 invariants but extend or optimize the original audit snapshot.

#### 4.5.1 Batch LLM Calls (Suggest + Retry)

| Behavior | Detail |
| -------- | ------ |
| Initial suggest | When `emptyFields.length ≥ 2`, a **single batch LLM call** via `buildBatchFieldPrompt()` returns all field values; on batch failure, falls back to sequential per-field calls |
| Batch retry | `generateRetrySuggestions()` issues a **single batch LLM call** via `buildBatchRetryPrompt()` for all queued fields (RT-INV-11: one HTTP request; service layer also batches LLM) |
| LLM JSON helpers | `extractJson` / `extractContent` in `llm-response-utils.ts` (replaces superseded bootstrap-parser coupling) |
| Sequential fallback gap | `COPILOT_LLM_CALL_GAP_MS` env var throttles **sequential fallback only**; irrelevant when batch succeeds |
| JSON parsing | `parse-copilot-value.ts` tolerates broken JSON from free-tier models (regex salvage + plain-text fallback) |

#### 4.5.2 Copilot Text LLM Provider

| Env var | Purpose |
| ------- | ------- |
| `COPILOT_TEXT_PROVIDER` | `"openrouter"` \| `"gemini"` (default: openrouter if `OPENROUTER_API_KEY` set, else gemini) |
| `OPENROUTER_API_KEY` | OpenRouter API key |
| `OPENROUTER_SUGGEST_MODEL` | Model slug (e.g. `openai/gpt-oss-120b:free`) |
| `GEMINI_API_KEY` / `GEMINI_SUGGEST_MODEL` | Gemini fallback |

Avatar / image generation remains on Gemini (`GEMINI_IMAGE_MODEL`) — out of SPEC-D2-002 scope.

#### 4.5.3 Work Title Context

- `/api/admin/ai/suggest` and `/api/admin/ai/suggest/retry` query `works.title` server-side and inject `workTitle` into all prompt builders.
- Prompts include anti cross-universe constraints (e.g. no Stark/Lannister in 三体).

#### 4.5.4 Client UX Amendments

| Change | File | Detail |
| ------ | ---- | ------ |
| `suggestErrors` state | `useCopilotSession.ts` | Surfaces partial failures, 429, and empty-field messages in panel |
| Scope change reset | `useCopilotSession.ts` | Changing scope field clears suggestions, errors, and retry queue |
| Empty-field message | `useCopilotSession.ts` | `NO_EMPTY_FIELDS` instead of misleading "all done" copy |
| Retry queue preservation | `useCopilotSession.ts` | Failed retry fields remain queued; `RETRY_FAILED` shown on HTTP error |
| Sheet drawer | All three Form components | `SuggestionPanel` rendered inside `Sheet` (right-side drawer); `showHeader={false}` when embedded |
| Error-only empty state | `SuggestionPanel.tsx` | Dedicated UI when only errors, no suggestions |

#### 4.5.5 Known SC-02 Gap

SPEC SC-02 requires accepted facts from the current session to inform subsequent suggestions. In batch initial suggest, all fields are generated in one call **before** any Accept — so `acceptedFacts` context is not injected into the first batch. Sequential fallback path can still benefit from per-field context. Full SC-02 fidelity awaits a future Source Connector / session-facts pipeline.

## 6. No Hardcoded Routing Verification

**Requirement (MD-01, AC-26):** No field name, entity type name, or classification value may appear as a string literal in Copilot routing logic.

**Verification method:** ripgrep across routing code files.

```bash
# Field name literals in routing logic — 0 matches
rg 'field\s*===\s*["'\'']\|===.*field\|if.*fieldName\|switch.*fieldName' \
  lib/ai/suggest-service.ts hooks/useCopilotSession.ts

# Routing in suggest-service: reads fr.copilot_route (pre-resolved by client)
# and meta?.copilot_route (from registry lookup) — not field name literals
grep "fr.copilot_route" lib/ai/suggest-service.ts  # route value comparison ✅
grep "meta?.copilot_route" lib/ai/suggest-service.ts  # registry lookup ✅
```

**Evidence:**
- `suggest-service.ts` routing logic: `if (fr.copilot_route === "fact")` and `const route = meta?.copilot_route ?? "narrative"` — these compare a **route value** (not a field name) derived from the registry.
- `useCopilotSession.ts`: does not inspect field names for routing — delegates to `getSuggestableFields()` in the registry.
- `getSuggestableFields()`: iterates `Object.keys(registry)` and calls `getEffectiveRoute()` for each — no field name literals in the filtering predicate.
- NarrativeRegen visibility: derived from `getClassification(entityType, field)` — not from `if (field === "description")`.
- `getFieldLabel()` provides display labels only; it does not participate in routing.

**Verdict: ✅ PASS — No hardcoded field name routing**
